### 3. 根因分析

- **3009 s 与 87 s 同源**：`embed-node.ts` 与 `llm-node.ts` 的 HTTP 调用已有内部超时（embed 60s、LLM 180s+），但 `aml.ts` 的 Search 层对 **单次外部调用没有独立超时**；一旦底层 socket 在重试/退避中不返回，Search 就会无限制悬挂。
- **87 s ≈ 3 × 29 s**：E 的 3 次 ~87 s 异常值形态，符合 HyDE 调用内部 29 s 级超时后外层无熔断、累计三次的循环；3009 s 则是同一缺陷在单 slice 高负载下的极端表现。
- **不是模型专属**：平台 flash 与 Agent Plan 基模型均可能触发；根因在共享调用层缺硬超时与降级策略。

### 4. 保险丝设计

`server/aml.ts` 已按以下顺序重构 Search：

1. **同步 BM25 兜底**：在发起任何外部调用前，先算出 `BM25(baseQuery, top_k * 2)` 并攥在手里；这一步永远不超过毫秒级。
2. **HyDE 增强**：调用 `expandQueryBatch`，外部预算 `AML_HYDE_TIMEOUT_MS=12000`；超时或失败则降级，最多重试 1 次。
3. **BM25 混合臂**：HyDE 成功后，同步重算 `BM25(hydeQuery, top_k * 2)`。
4. **向量臂**：调用 `embedTexts` + `topByVector`，外部预算 `AML_EMBED_TIMEOUT_MS=10000`；超时或失败则降级，最多重试 1 次。
5. **总预算熔断**：任何阶段 `Date.now() >= start + AML_SEARCH_DEADLINE_MS=25000` 立即返回 BM25 兜底。
6. **降级日志**：只记录 `user_id`、耗时、哪一路降级，不记录 query 正文或返回内容。

正常路径行为保持不变：p95 3.7 s 远低于 25 s 预算，保险丝仅在真实悬挂时触发。

### 6. 平台 pipeline 契约要点

来自公开仓库 `github.com/AML-memory/agent-memory-leaderboard` 的 `data/*/pipeline.py`：

- **作答模板**把我们 Search 返回的 `content` 原文渲染进 prompt，并提示模型把相对时间按记忆时间戳转成绝对日期；我们的 `[YYYY-MM-DD]` 内容前缀正好支撑这一转换。
- **判分规则**是宽松包含 + 不矛盾，但**时间粒度严格**；返回记忆的时间戳前缀对判分至关重要。
- **Search 超时上限**未在公开仓库声明，按未知处理；因此保险丝的总预算 25 s 是防御性设计，到期即返回 BM25 兜底，确保不空响应。
